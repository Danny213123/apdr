# Phase 21.1: Repository Footprint and Download Size Reduction - Context

**Gathered:** 2026-04-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Reduce the repo's disk footprint before the rest of v2.4 continues, with emphasis on `tools/`. This phase should shrink both fresh source and GitHub-download size and large local generated/build footprints, especially where tracked tool artifacts or default in-tree caches make the checkout balloon. This phase is not where we decide Docker-first `llm` policy, rework benchmark UI surfaces, or redesign the overall build architecture.

</domain>

<decisions>
## Implementation Decisions

### Footprint surface
- **D-01:** Phase 21.1 should target both fresh source/download size and large local post-build footprint, not only one of them.
- **D-02:** Prioritize high-impact bytes under `tools/` before chasing smaller wins elsewhere in the repo.

### Priority bytes
- **D-03:** Tracked generated build outputs under `tools/apdr/target-*` are first-class scope and should not keep inflating source checkout and GitHub-download size.
- **D-04:** Large local generated directories such as `tools/apdr/target` and `tools/apdr/.apdr-cache` are also first-class scope and should be avoided, relocated, or safely reclaimable.

### Delivery shape
- **D-05:** Prefer structural or default changes that keep the tree smaller by default rather than only documenting manual cleanup commands.
- **D-06:** Any cleanup or relocation path must preserve normal local APDR development and benchmark workflows; do not solve footprint by making the tool harder to rebuild or debug.

### Scope guardrails
- **D-07:** Start with `tools/`, especially `tools/apdr`, and broaden only if evidence shows other directories dominate the remaining footprint.
- **D-08:** Do not turn this phase into a full Git-history rewrite or external artifact-hosting migration unless meaningful wins are impossible without that larger intervention; treat those as deferred unless proven necessary.

### the agent's Discretion
- Exact mechanism for reducing tracked build-output footprint, as long as it removes avoidable heavyweight bytes from normal source distribution.
- Exact cleanup, relocation, or configuration surface for large local APDR caches and build outputs, as long as the supported path is easy to discover and safe to use.
- Exact before/after evidence format, as long as the planner locks a truthful size-comparison proof and does not rely on hand-wavy claims.

</decisions>

<specifics>
## Specific Ideas

- Current local evidence on 2026-04-01 shows `tools` at about `29G`, with `tools/apdr/.apdr-cache` at about `15G` and `tools/apdr/target` at about `6.7G`.
- The repo also contains tracked `tools/apdr/target-fix-*` and `tools/apdr/target-test-*` trees, so the GitHub/source-download problem is real and not just a local ignored-cache issue.
- The user wants this phase inserted before the rest of the new v2.4 phases rather than buried inside Docker-first routing work.
- The practical user complaint is disk pressure: the project is taking too much space locally, and downloading it from GitHub is heavier than it should be.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `tools/apdr/.gitignore`: already ignores `target/` and `.apdr-cache/`, so the phase can separate ignored local growth from wrongly tracked target-style directories.
- `.gitignore`: the repo already ignores many generic build outputs, which means the biggest remaining problem is likely APDR-specific layout or tracked exceptions, not missing generic ignore rules alone.
- `tools/apdr/README.md`: existing docs already talk about cache behavior and cleanup expectations, so the phase can tighten those instead of inventing a new operator story from scratch.

### Established Patterns
- Milestone claims should be backed by artifact-level evidence, so footprint reduction needs before/after size proof rather than a vague "repo feels smaller" statement.
- Compatibility remains a hard constraint; footprint work cannot silently break Windows, Docker, or benchmark flows.
- The repo already distinguishes requested behavior from actual routed behavior in benchmark artifacts; similarly, this phase should distinguish source-distributed bytes from local generated bytes instead of mixing them together.

### Integration Points
- `tools/apdr` build and test workflow configuration if target directories or output layout change.
- `scripts/` or repo-root helper surfaces if a supported cleanup or relocation command is added.
- Docs and runbooks that tell operators and developers where heavyweight outputs live and how to reclaim them safely.

</code_context>
